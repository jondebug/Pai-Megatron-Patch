3. Implementation autopsy — the RL was structurally unable to win

Hypothesis under test: H1+H2 unified at the code level: does the implementation permit per-token credit assignment on the true objective at all?

Method: Direct code reading of rl_trajectory.py (loss paths, reward-type constraints, update structure), cross-checked against the 30-cell telemetry (clip fraction, approx KL, advantage std, value loss).

Reading the actual RL core (megatron_patch/model/qwen3_moe/moe/rl_trajectory.py, 1634 lines — outside the original audit corpus) explains the telemetry exactly:

  • self.ppo_epochs = 1 (line 208). One optimization epoch per rollout means the importance ratio is computed against the same policy that produced the data: ratio ≡ 1, clipping can never activate, approx-KL ≡ 0. The telemetry shows exactly that — clip_fraction = 0.0 and approx_kl = 0.0 in every one of 30 cells. The method as run is REINFORCE-with-baseline, not PPO. (Multi-epoch machinery exists — run_extra_ppo_epochs — but was never enabled in any sweep.)
  • Max-type rewards are forced batch-scalar (lines 402–416: critical_path, topn_load, entropy raise if per-token is requested). In the scalar path (_compute_ppo_loss_scalar) returns and baselines are .mean()-ed per layer: every token in the batch shares one advantage per layer. The gradient is then "push all chosen assignments in layer ℓ up/down uniformly" — a layer-weighted balance pressure with zero per-token credit assignment.
  • The only per-token-credit reward is the surrogate (per_token_load_weighted, auto per-token at line 396) — whose trajectory tracks the aux objective (D2).
  • Advantage whitening across layers (unit std each step, telemetry: advantage_std ≈ 0.99999...) discards the scale of the load signal; the critic chases a moving whitened target (value-loss grows ~47× over training instead of converging).
surrogate objective (≈ aux)true CP / max objective
per-token credit assignmentper_token_load_weighted — this is where every winning RL cell lives EMPTY — structurally unreachable in the current code
batch-scalar (per-layer) creditentropy (r33)critical_path, topn_load — underperformed

Why parity follows: the only configuration with usable credit assignment optimizes (approximately) the aux objective, with a REINFORCE estimator — i.e., a noisier re-parametrization of the aux loss. The configurations that target the true CP objective cannot tell which token to reroute. RL never had a mechanism by which it could beat aux in the bulk region.

Implication (the fix occupies the empty quadrant): a counterfactual per-token CP advantage — for each token, ΔCP if it were rerouted to its next-best expert (exactly computable per layer, since only tokens on argmax experts have nonzero marginal effect) — provides dense, exact credit assignment for the true objective. Combine with ppo_epochs≥2 (making PPO actually PPO) and un-whitened (scale-preserving) advantages. These are three independent, testable upgrades.

CONFIRMED   CONFIRMED — ppo_epochs=1 (REINFORCE in practice), max-objectives restricted to per-layer scalar advantages (no token credit), and the only per-token reward is an aux-like surrogate. The winning quadrant (per-token credit x true CP) is empty.

Literature-grounded method upgrade (fills the empty quadrant from section 3):

  1. Exact difference rewards, critic-free (Dr.Reinforce): when the global reward is an analytic function of decisions — CP is — the counterfactual advantage is computed by differencing the reward function itself. Caveat (verified): max-objectives give zero credit to non-bottleneck tokens → difference a smoothed aggregate (LogSumExp over expert loads); monitor corr vs aux objective so smoothing doesn't recreate H1.

  3. Enable real PPO (ppo_epochs≥2) with router-shift control: R3 rollout-routing-replay (Megatron-LM PR #4168 — our stack) or RSPO stop-grad down-weighting; never backprop through router-derived ratios (collapses at ~40 steps).
